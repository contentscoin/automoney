# 08. 콘텐츠 제작 표준 운영 절차

## 1. 목적과 적용 범위

이 문서는 상품 콘텐츠를 누가 언제 다시 제작해도 같은 **품질 기준**으로 생성·검토할 수 있도록 입력, 실행, 판정, 실패 대응을 고정한 SOP입니다. `/dashboard/workflow`에서 만드는 최대 10개 상품의 SNS·블로그 콘텐츠에 적용합니다.

여기서 “동일한 품질”은 문장을 매번 똑같이 복제한다는 뜻이 아닙니다. 다음 조건이 모두 같고, 모든 산출물이 같은 품질 게이트를 통과한다는 뜻입니다.

- 같은 제작 기준 ID와 버전
- 같은 정규화된 브리프, 상품·이미지 스냅샷, 채널 목록
- 같은 워크플로·프롬프트·품질 정책 버전
- Codex 생성, 채널별 규격 준수, 품질 점수 92점 이상
- 자동 차단 위반 0건과 카탈로그 원본을 대조한 사람 승인
- 예상 산출물 수와 실제 통과 산출물 수 일치

문구의 창의적 표현은 달라질 수 있습니다. 재현 대상은 표현의 바이트값이 아니라 입력 계약과 통과 기준입니다.

## 2. 핵심 개념

### 제작 기준(Standard)

품질을 판정하는 버전 계약입니다. 실행을 등록할 때 복사되며, 이후 기본 기준이 바뀌어도 기존 실행은 영향을 받지 않습니다.

기본 기준은 다음과 같습니다.

| 항목 | 기본값 |
|---|---|
| 기준 | 아뜨랑스 기본 콘텐츠 기준 v2.0.0 |
| 생성기 | Codex 필수, 템플릿 대체 불가 |
| 통과 점수 | 92점 이상 |
| 품질 시도 | 최대 3회 |
| 이모지 | 채널당 2개 이하 |
| 사실 근거 | 등록된 상품 카탈로그와 승인된 콘텐츠 원자만 |
| 광고 표기 | 누락 시 서버가 `#광고`를 필수 보정하고 최종 결과를 다시 검사 |
| 금지 주장 | 최저가·순위·직접 착용 경험·절대 표현·효능, 근거 없는 배송/교환/자체제작·소재 함량·착용 효과 주장 |

### 제작 브리프(Brief)

한 실행의 의도를 정하는 입력입니다.

- 목표: 상품 발견 / 반응 유도 / 상품 링크 전환
- 말투: 채널에 자연스럽게 / 정중한 존댓말 / 친근한 말투
- CTA: 댓글 / 저장 / 상품 링크 확인
- 대상 고객: 기본 `20~30대 여성 패션 관심 고객`
- 핵심 메시지: 선택 입력, 최대 300자

핵심 메시지도 사실 근거 규칙의 적용을 받습니다. 카탈로그에서 확인되지 않는 내용을 사람이 입력했다고 해서 검증된 사실이 되지 않습니다.

### 제작 실행(Run)

상품, 채널, 브리프, 제작 기준을 한 번에 고정한 작업 단위입니다. 실행에는 `runId`, 실행 명세 해시(`manifestHash`), 예상 산출물 수, 연결된 작업 ID, 생성·승인 수가 남습니다. 각 조각에는 원자·플레이북·거절 패턴까지 포함한 `jobInputHash`, 정규화 결과의 `outputHash`, 데스크톱 버전, provider·engine·model·Codex CLI 버전(`cliVersion`)과 시도 번호가 별도로 남습니다. model 또는 CLI 정보를 실행 환경에서 확인하지 못한 경우에는 임의 값을 채우지 않고 `null`로 남기므로, 재현 조사 때 데스크톱 로그와 함께 확인합니다. 콘텐츠는 `runId` 전용 쿼리로 조회하므로 오래된 실행도 잘리거나 다른 실행과 섞이지 않습니다.

예상 산출물 수는 다음과 같습니다.

```text
예상 산출물 수 = 선택 상품 수 × 선택 채널 수
```

## 3. 역할과 책임

- 운영자: 상품 카탈로그의 이름·가격·카테고리·이미지·URL과 사용 권한을 최신 상태로 유지합니다.
- 제작자: 브리프를 정하고 원본 상품 페이지와 최종 문구·이미지·링크를 대조합니다.
- 시스템: 입력 스냅샷, Codex 실행, 채널 규격, 광고 표기, 금칙·품질 점수, 실행별 산출물 수를 검사합니다.
- 게시 계정 소유자: 실제 게시 직전에 SNS 계정, 공개 범위, 최종 미리보기를 확인하고 승인합니다.

시스템 점수는 이미지 사용권이나 사람에게 자연스러운 뉘앙스를 법적·편집적으로 보증하지 않습니다. 이 항목은 반드시 사람이 확인합니다.

## 4. 실행 전 준비 조건

다음 항목을 모두 충족한 후 생성합니다.

1. PC 앱 0.1.13 이상이 `온라인`입니다. 0.1.12 이하는 계정 identity, JIT 재검증, 게시 시도 marker, canonical receipt를 모두 지원하지 않으므로 실게시 작업을 claim할 수 없습니다.
2. PC 앱에서 Codex 로그인이 확인됩니다.
3. 홍보할 상품이 1~10개이고 모두 판매 가능한 상태입니다.
4. 각 상품에 활성 마케팅 링크가 있습니다.
5. 이미지가 필요한 채널에는 사용 가능한 상품 이미지가 있습니다.
6. 대상 고객이 비어 있지 않고 채널을 하나 이상 선택했습니다.
7. 핵심 메시지에 근거 없는 배송·교환·순위·직접 착용 주장이 없습니다.
8. 실제 캠페인이라면 상품 이미지와 상세 콘텐츠의 마케팅 재사용 권한을 확인했습니다.
9. Instagram Reels 또는 TikTok을 선택했다면 게시 가능한 HTTPS 동영상 URL 1개를 별도로 준비합니다. 현재 제작 실행은 대본을 생성하지만 동영상 파일을 렌더링하거나 업로드하지 않습니다.

조건이 충족되지 않으면 생성 버튼을 우회하지 말고 화면에 안내된 연결·링크 문제부터 해결합니다.

## 5. 표준 제작 SOP

### 1단계 — 제작 기준과 브리프 확정

1. `/dashboard/workflow`에서 **새 제작 시작**을 선택합니다.
2. 화면의 제작 기준 이름·버전, Codex 필수 여부, 통과 점수, 최대 시도 횟수를 확인합니다.
3. 목표, 말투, CTA, 대상 고객을 선택합니다.
4. 강조할 사실이 있을 때만 핵심 메시지를 입력합니다. 원본 상품 페이지에서 확인할 수 없는 문구는 입력하지 않습니다.

생성 요청 후 브리프와 기준은 실행 스냅샷으로 고정됩니다. 수정이 필요하면 기존 실행을 덮어쓰지 않고 새 실행을 만듭니다.

### 2단계 — 상품 선택

1. 상품을 1~10개 선택합니다.
2. 상품명, 판매가, 카테고리, 이미지와 **아뜨랑스 상품 보기** 원본을 확인합니다.
3. 잘못되거나 오래된 상품 정보는 콘텐츠 문구로 보정하지 말고 카탈로그를 먼저 수정합니다.

최근 실행을 열면 해당 실행의 상품이 복원되고 잠깁니다. 다른 상품을 선택하려면 새 제작을 시작합니다.

### 3단계 — 마케팅 링크 준비

1. 선택 상품 수와 준비된 링크 수가 같은지 확인합니다.
2. 없는 링크는 **선택 상품 링크 일괄 발급**으로 준비합니다.
3. MOCK/DEMO 링크에는 “수익 추적 안 됨”이 표시됩니다. 데모 링크를 실제 정산 증빙에 사용하지 않습니다.

콘텐츠의 상품과 다른 상품 링크, 비활성 링크, 다른 사용자 링크는 게시 단계에서 다시 차단됩니다.

### 4단계 — 채널 선택과 제작 실행

1. 필요한 채널만 선택합니다. 기본값은 Threads와 Instagram Feed입니다.
2. PC 온라인, Codex 로그인, 모든 링크 준비 상태를 다시 확인합니다.
3. **기준 고정 후 생성**을 한 번 선택합니다.
4. 반환된 `runId`를 현재 실행으로 저장하고, 이후 진행률은 그 실행의 작업과 콘텐츠만 집계합니다.

버튼을 연속으로 누르거나 작업 페이지에서 같은 요청을 임의로 중복 등록하지 않습니다. 실행이 만들어졌다면 완료 또는 실패 상태가 확정될 때까지 해당 실행을 관찰합니다.

### 5단계 — 진행 상태와 결과 검토

진행 패널에서 다음 수치를 확인합니다.

- 예상 결과: 상품 수 × 채널 수
- 생성: 현재 실행에 실제 저장된 콘텐츠 수
- 기준 통과: 자동 게이트 통과 후 사람이 승인한 수
- 검토 필요: 아직 사람 승인을 받지 않았거나 자동 게이트를 통과하지 못한 수
- 실패 작업: 실행 실패 또는 취소된 상품 작업 수

상품별 행에서 링크, 생성 작업 상태, 채널 결과, 통과 수를 대조합니다. 예를 들어 10개 상품과 2개 채널이면 예상 결과는 20개이며, 19개만 생성되면 완료가 아닙니다.

각 콘텐츠에서 다음을 확인합니다.

#### 시스템 검사

- 생성 출처가 Codex인지
- 제작 기준·품질 정책 버전, 시도 번호, provider·engine·model·Codex CLI 버전
- 점수 92점 이상인지
- 광고 표기가 있는지
- 채널 최소·최대 길이, 해시태그, 숏폼 대본 80자·3개 이상 시간/단계 큐 규격을 지켰는지
- 상품 식별 표현과 입력한 핵심 메시지가 반영됐는지
- 금지 표현과 근거 없는 상품 사실이 없는지
- 요청 채널별 결과가 정확히 한 개씩 있는지

#### 사람의 최종 검사

- **상품 사실 확인** (`productFacts`): 상품명·가격·특징이 화면에 제시된 동결 상품 근거와 원본 상품 페이지에 일치하는지
- **광고 표기 확인** (`adDisclosure`): `#광고`와 CTA·마케팅 링크 목적지가 일치하는지
- **미디어 권리·채널 적합성 확인** (`mediaRightsAndFit`): 해당 상품의 미디어이고 마케팅 사용이 허용되며 크롭·인물·가격 노출·형식이 채널에 맞는지
- **최종 문구 확인** (`finalCopy`): 한국어가 자연스럽고 대상·말투·해시태그·숏폼 대본이 실제 게시 화면에 적합한지

자동 게이트를 통과해도 결과는 `DRAFT`입니다. 승인 창에서 위 네 가지 체크리스트를 모두 선택해야 하며, 화면이 읽은 정확한 revision의 `expectedOutputHash`와 서버가 다시 계산한 `outputHash`가 일치해야 승인됩니다. 승인 시 actor·시각·`outputHash`·네 체크 항목·본문/해시태그/대본/미디어/점수 snapshot을 `contentReviewEvents`에 새 행으로 기록합니다. 이 review event는 과거 행을 덮어쓰지 않는 불변 감사 기록입니다.

승인은 `DRAFT` 상태에서만 가능합니다. 수정한 콘텐츠는 다시 `DRAFT`가 되고 `outputHash`가 바뀌므로 기존 검토 화면이나 승인은 재사용할 수 없습니다. `RETIRED` 결과도 곧바로 재승인할 수 없으며 먼저 수정해 새 revision을 만들어야 합니다. 자동 품질 검사를 다시 통과한 뒤 네 항목을 새로 확인해 승인해야 합니다. 수퍼어드민도 차단 위반이나 stale `expectedOutputHash`를 승인으로 우회할 수 없습니다.

운영 공유(`SHARED`) 중인 조각은 수동 작성본을 포함해 편집 즉시 `PRIVATE`로 되돌아갑니다. 새 revision을 승인한 뒤 수퍼어드민이 다시 공유해야 다른 사용자가 볼 수 있습니다. `pieceId`로 즉시 게시하거나 예약할 때에는 수동 작성본도 승인된 본문·미디어와 정확히 같아야 하며, 서버는 해당 revision의 output/snapshot hash를 저장해 다른 본문을 같은 조각의 성과로 귀속하지 않습니다.

#### 숏폼 미디어 준비

- `INSTAGRAM_REEL`과 `TIKTOK`은 게시 payload에 검증 가능한 HTTPS 동영상 URL이 정확히 1개 있어야 합니다.
- 허용되는 동영상 식별 형식은 URL 경로가 `.mp4`, `.mov`, `.m4v`, `.webm` 중 하나인 경우입니다. 정적 이미지, HTTP URL, 종류를 판별할 수 없는 URL, 0개 또는 2개 이상은 게시 준비 단계에서 차단됩니다.
- 현재 자동 제작은 숏폼 대본까지만 생성하며 동영상 변환·호스팅을 하지 않습니다. 카드의 콘텐츠 수정에서 기존 정적 상품 이미지를 지우고 운영자가 준비한 HTTPS 동영상 URL 1개로 수동 교체한 뒤 저장·재검토·재승인합니다.

### 6단계 — 테스트 게시와 실제 게시

1. 실행의 `기준 통과` 수가 `예상 결과` 수와 같고 상태가 `COMPLETED`인지 확인합니다.
2. **테스트 게시 준비**로 이동합니다.
3. `테스트 실행(실제 게시 안 함)`이 켜져 있는지 확인합니다.
4. 게시 계정, 본문, 미디어, 같은 상품의 링크를 확인한 뒤 승인 대기 작업을 등록합니다.
5. 작업 결과에서 dry-run 성공을 확인합니다.

dry-run은 `LIVE_PUBLISH_ENABLED` 값과 무관하게 허용됩니다. 실제 게시가 필요한 경우에만 서버 환경의 `LIVE_PUBLISH_ENABLED=true`를 명시적으로 설정하고, dry-run을 끈 뒤 계정 소유자가 정확한 payload hash를 다시 승인합니다. 변수가 없거나 `false`이면 fail-closed로 실게시 등록·예약 실행·preflight가 차단됩니다. 데모 SOP의 완료 지점은 dry-run이며 외부 SNS 게시가 아닙니다.

dry-run에서는 레시피와 오토파일럿 모두 게시·공유·제출 click과 Enter 계열 단축키를 실행하지 않습니다. 모델의 `done` 응답이나 모델이 제시한 URL도 게시 성공 증거로 사용하지 않습니다. 데스크톱의 로컬 `AUTOMONEY_DRY_RUN=1`은 비상 안전장치일 뿐 서버가 보낸 live payload를 dry-run 성공으로 바꾸지 않으며, 이 조합은 `LOCAL_DRY_RUN_OVERRIDE`로 명시적으로 실패합니다. 정상적인 테스트 실행은 항상 작업 payload의 `dryRun=true`로 등록합니다.

live 게시에는 다음 세 안전 게이트가 모두 적용됩니다.

1. **Account identity**: 선택한 space에 저장된 handle과 현재 브라우저 세션에서 다시 읽은 handle이 둘 다 존재하고 정규화 후 일치해야 합니다. Meta API와 브라우저 fallback처럼 같은 게시 계정의 경로는 동일 publication identity로 reservation을 공유합니다.
2. **원자적 게시 시도 승인**: handler 시작 시 검사한 값만 재사용하지 않습니다. 실제 브라우저 submit 또는 Meta API publish 호출 직전에 서버가 `LIVE_PUBLISH_ENABLED`, 승인 payload hash/만료, 사용자·space, 콘텐츠 revision과 사람 검토 증거, 링크 활성 상태, 예약 revision, 계정 identity, lease와 quota reservation을 한 mutation에서 다시 검증하고 `publishAttemptedAt`을 기록합니다. 이 marker가 없거나 이미 한 번 기록된 작업은 live 성공 또는 두 번째 submit으로 진행할 수 없습니다.
3. **Canonical receipt**: submit 직전 기준선에 없던 새 게시 URL만 짧은 검증 시간 안에 수집합니다. URL은 대상 플랫폼의 canonical post 형식이어야 하고, 플랫폼 URL이 계정 handle을 제공하는 경우 선택한 계정과도 일치해야 합니다. 서버도 live 성공 completion의 canonical `postUrl`을 다시 검사하며, 영수증이 없거나 확인할 수 없으면 성공으로 처리하지 않고 `UNCERTAIN` 조정 대상으로 남깁니다.

Meta API 실패로 브라우저 대체 작업이 만들어져도 원 작업이 사람 승인을 요구했다면 대체 payload는 새 승인을 다시 받아야 합니다. 원 작업이나 대체 작업 중 하나를 취소하면 같은 `rootJobId` 계열의 승인 대기·대기·실행 중 작업에 취소가 전파되며, JIT 게시 게이트도 root 취소 표식을 다시 확인합니다.

현재 브라우저 전용 X·TikTok·Naver 계정은 provider가 서명한 stable account ID를 수집하지 못하므로 publication identity가 Automoney 테넌트별 handle로 격리됩니다. 따라서 동일한 실제 외부 계정을 서로 다른 Automoney 테넌트가 연결하면 전역 중복 게시 차단을 보장하지 못합니다. 공개 handle을 곧바로 전역 key로 쓰면 다른 테넌트가 handle을 사칭해 실제 소유자의 게시를 막는 DoS가 가능하므로 그렇게 합치지 않습니다. 해당 계정은 한 Automoney 테넌트에서만 운영하고, 향후 외부 계정 소유권 registry 또는 provider-signed stable ID 수집이 도입되기 전까지 이 제한을 배포 위험으로 추적합니다.

### MCP·Telegram 등록 안전 규칙

- MCP `post_publish`와 `post_schedule`은 `confirmed=true`가 없으면 미리보기만 반환합니다. 실제 확정 호출에는 8~100자의 `clientRequestId`가 필수이며, 같은 키와 같은 payload의 재호출은 같은 작업을 반환하고 다른 payload 재사용은 충돌로 거부됩니다.
- 예약의 `autoApprove=true`는 반복적으로 사람 승인 없이 게시하므로 `confirmed=true`와 별도의 `confirmAutoApprove=true`를 모두 요구합니다. 둘 중 하나라도 없으면 예약을 만들지 않고 확인 응답만 반환합니다.
- Telegram webhook은 유효한 `update_id`가 없으면 거부합니다. 이미 처리한 `update_id`는 처리 원장에서 재생으로 판정해 `/post` 작업, 승인 callback, 감사 event, 봇 응답을 중복 실행하지 않습니다.

## 6. 실행 상태 정의

| 상태 | 의미 | 다음 행동 |
|---|---|---|
| `QUEUED` | 실행이 등록됐고 PC 작업을 기다림 | PC 온라인과 에이전트 상태 확인 |
| `RUNNING` | 하나 이상의 상품 작업이 처리 중 | 중복 요청 없이 진행률 관찰 |
| `REVIEW_REQUIRED` | 작업은 끝났지만 누락·초안·품질 미달이 있음 | 상품별 오류와 품질 보고서 수정 |
| `FAILED` | 모든 작업이 실패하고 결과가 없음 | 원인 해결 후 같은 기준으로 새 실행 |
| `COMPLETED` | 모든 예상 결과가 자동 게이트를 통과하고 사람 승인까지 완료 | dry-run |

`COMPLETED`는 시스템 품질 계약과 화면의 사람 검토 승인이 끝났다는 뜻입니다. 저작권·법무 승인이나 실제 SNS 게시 승인을 대신하지는 않습니다.

## 7. 실패와 재시도 절차

실패했을 때 기존 실행의 입력이나 결과를 직접 바꾸지 않습니다.

1. `/dashboard/jobs`에서 실패 코드와 메시지를 확인합니다.
2. 원인을 아래 순서로 분류합니다.
   - PC 오프라인 또는 페어링 문제
   - Codex 미설치·미로그인·응답 파싱 실패
   - 상품·링크·이미지 누락
   - 요청 채널 결과 누락
   - 3회 시도 후에도 92점 미달 또는 정책 위반
   - 실행 lease 만료 3회로 `EXECUTION_RETRY_EXHAUSTED`
   - 에이전트를 찾지 못한 채 큐에서 24시간 경과해 `DEVICE_OFFLINE_TIMEOUT`
3. 연결이나 카탈로그 같은 원인을 먼저 해결합니다.
4. **같은 기준으로 재시도 준비**를 선택해 상품·채널·브리프를 복사합니다.
5. 복사된 입력을 확인하고 새 실행을 등록합니다.

재시도는 새 `runId`를 가져야 합니다. 이전 실행은 감사 이력으로 남기고, 새 실행 결과와 합쳐 완료로 계산하지 않습니다. 일부 성공 결과가 있어도 실패 실행의 결과와 새 실행 결과를 수동으로 섞어 “전체 통과”로 간주하지 않습니다.

비게시 작업은 lease가 만료되면 다시 큐에 들어가지만 세 번째 실행 시도까지 끝나면 terminal `FAILED`가 됩니다. 한 번도 실행되지 못한 `QUEUED` 작업도 생성 후 24시간이 지나면 terminal `FAILED`가 되며, 연결된 콘텐츠 run의 완료·실패 집계도 갱신됩니다. 자동 재큐잉을 계속 반복하지 말고 원인을 해결한 뒤 새 실행을 만듭니다.

`post.publish`는 외부 부수효과가 있을 수 있으므로 lease 상실, 디바이스 해제·교체, submit 이후 응답 불명확 상황에서 재큐잉하지 않습니다. 잡은 terminal `FAILED`, `publishPhase`와 reservation은 `UNCERTAIN`으로 두고 운영자는 `/dashboard/jobs`에서 해당 SNS 계정의 실제 게시물·시각·본문을 직접 대조합니다. 게시를 확인한 경우 canonical 게시 URL과 함께 **게시됨**으로 조정해 reservation을 `COMMITTED`로 만들고 실적 수집을 시작합니다. 게시물이 없음을 확인해 **게시되지 않음**으로 조정해도 reservation은 원래 intent 만료와 조정 후 15분 중 더 늦은 시각까지 `UNCERTAIN`을 유지한 뒤 자동 해제됩니다. 화면에 표시된 안전 대기 종료와 `RELEASED`를 확인한 후에만 새 payload와 새 승인의 게시 작업을 만듭니다. 어느 경우에도 기존 terminal 잡을 되살리거나 확인 전에 같은 콘텐츠를 다시 게시하지 않습니다. 조정 actor·시각·결과·증거 URL은 감사 기록에 남습니다.

### 이전 품질 계약 콘텐츠 격리

`runId`가 없으면서 `generatedBy`가 `manual`이 아닌 이전 자동 생성물은 현재의 동결 기준, 출력 hash, 사람 검토 event를 증명할 수 없으므로 격리됩니다. 수퍼어드민도 이 콘텐츠를 편집해 manual로 바꾸거나 승인·공유·복사·게시해 우회할 수 없습니다. 원문은 감사·참고용으로 보존하되, 운영에 쓰려면 현재 제작 워크플로에서 새 `runId`로 다시 생성하고 검토합니다. 사람이 직접 작성한 `manual` 콘텐츠는 별도 수동 품질 게이트를 따릅니다.

### 공유 콘텐츠 복사본 재검토

승인된 공유 콘텐츠를 **내 콘텐츠로 가져오기**로 복사해도 원본 승인이 상속되지는 않습니다. 복사본은 `PRIVATE`·`DRAFT`로 생성되고 기존 승인자·승인 시각·review checklist는 제거됩니다. 원본의 동결 제작 증거는 `evidenceRunId`, `copiedFromPieceId`, production metadata로 보존하되, 복사본의 현재 `outputHash`를 기준으로 상품 사실·광고 표기·미디어 권리와 적합성·최종 문구 네 항목을 모두 다시 검토하고 새 review event로 승인해야 공유·게시할 수 있습니다.

## 8. 완료 정의(Definition of Done)

콘텐츠 제작 실행은 다음 조건을 모두 충족해야 완료입니다.

- [ ] 상품 1~10개와 채널 1개 이상이 실행에 고정됨
- [ ] 제작 기준·브리프·상품/이미지 스냅샷·실행 명세 해시가 저장됨
- [ ] 각 결과에 잡 입력 해시·출력 해시·데스크톱 버전·provider·engine·model·Codex CLI 버전·시도 번호가 저장됨
- [ ] 상품마다 활성 마케팅 링크가 있음
- [ ] 모든 작업이 종료됐고 실패 작업이 없음
- [ ] 실제 산출물 수가 예상 산출물 수와 같음
- [ ] 모든 산출물이 조각별 provenance가 있는 Codex 생성이며 품질 점수 92점 이상
- [ ] 차단 위반, 근거 없는 사실, 광고 표기 누락이 없음
- [ ] 상품 사실·광고 표기·미디어 권리와 적합성·최종 문구의 네 체크리스트를 모두 확인하고 현재 `expectedOutputHash`로 승인함
- [ ] 각 승인에 불변 review event와 승인 당시 콘텐츠 snapshot이 저장됨
- [ ] Reels·TikTok은 정적 이미지를 제거하고 검증 가능한 HTTPS 동영상 URL 1개로 교체함
- [ ] 데모에서는 dry-run이 성공했고 외부 SNS 게시가 없음
- [ ] 실제 게시에서는 계정 소유자가 최종 미리보기를 승인함
- [ ] 공유 콘텐츠 복사본을 사용했다면 `DRAFT` 복사본의 현재 output hash로 네 항목을 재검토·재승인함
- [ ] 실제 게시 성공에는 JIT preflight와 대상 플랫폼의 새 canonical receipt가 있음

하나라도 충족하지 않으면 `완료`로 보고하지 않습니다.

## 9. 데이터와 법적 경계

- 상품명·가격·카테고리·이미지·상세 URL처럼 등록된 카탈로그 값만 생성 근거로 사용합니다.
- “오늘출발”, “무료 교환”, “자체제작”, 순위, 최저가, 직접 착용 경험은 별도 근거 필드가 없으면 생성하지 않습니다.
- 아뜨랑스 상품 이미지와 상세 콘텐츠의 2차 가공·재게시 범위는 계약으로 확정하기 전 공개 캠페인에 사용하지 않습니다.
- 임시 링크의 `am_tc` 코드는 UI·클릭 로그 시연용이며 주문 귀속·수수료 정산 증빙이 아닙니다.
- `contentReviewEvents`와 기존 실행·조각 provenance는 승인 취소나 재생성을 이유로 삭제·덮어쓰지 않습니다. 정정은 새 revision과 새 event로 남깁니다.

## 10. 실서비스 전 외부 선행 조건

- 아뜨랑스 파트너 API, 실제 tracking code, 주문 웹훅 및 월 정산 파일 규격 합의
- 상품 이미지·매거진 본문의 마케팅 재사용 권한 확인
- Meta 앱 사업자 인증·앱 리뷰 및 각 SNS 실제 계정 스모크 테스트
- Windows/macOS 코드 서명과 개인정보·표시광고·정산 관련 법무 검토
- 승인 이후에도 원격 미디어 URL의 바이트가 바뀔 수 있으므로, 실서비스 live 게시 전에는 승인 시점 파일을 자사 immutable object storage로 복사하고 content hash를 payload와 review event에 결합하는 미디어 고정 계층 도입

현재 구현은 URL 문자열·확장자·채널 규격을 고정하지만 원격 URL이 반환하는 실제 바이트까지 동결하지는 않습니다. 이 계층이 도입되기 전에는 `LIVE_PUBLISH_ENABLED=false`를 기본값으로 유지하고 제한된 사람이 최종 미디어를 직접 확인하는 dry-run/승인형 베타만 운영합니다.
